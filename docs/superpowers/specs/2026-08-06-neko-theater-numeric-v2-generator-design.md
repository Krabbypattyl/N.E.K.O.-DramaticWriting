## 1. 产品目标

N.E.K.O.-DramaticWriting Numeric v2 生成器只负责作者控制的宏观剧情和运行边界：

- 故事背景和身份关系；
- 正式剧情节点；
- 分支剧情；
- 结局；
- 本剧可使用的数值；
- 每个数值增加、减少的作者依据；
- 分支和结局的数值条件；
- 进入目标剧情时必须发生和不得改变的内容。

N.E.K.O.-DramaticWriting 不再生成：

- 每个节点的自然语言 interaction examples；
- `available_interaction_ids`；
- 作者预写的运行时 Choice；
- 每轮对话内容；
- 每轮推荐选项；
- 玩家输入分类规则；
- N.E.K.O Session、Ledger 或当前数值。

一句话定位：

> N.E.K.O.-DramaticWriting 写“故事地图和进入条件”，N.E.K.O 演“地图之间发生的过程”。

作者侧的默认体验不应要求用户先理解图编辑器和数值比较式。首次生成仍只创建主线与一个 Normal
结局；后续支线优先通过“先选终点、再反推过程”的向导生成，手动节点和路线编辑保留为高级能力。

## 3. 生成器职责边界

### 3.1 初次主线模型负责生成

- 世界背景、双主角身份和关系动力；
- 目标篇幅范围内的主线章节；
- 每章1—6项 `ordered_goals` 作者事件，明确主体、前提、结果与发生时点；它们不成为Runtime逐项任务锁；
- 一个从主线自然收束的 Normal 结局；
- 初始关系和整体氛围标签。

初次主线模型不返回 Numeric v2 完整合同，不生成支线、route gate、metric 或阈值。新稿用户消息包含
`core_idea`、目标篇幅 `length` 和生成姓名快照 `cast_names`；旧无姓名检查点沿原槽位续写。

其中 `world.background` 是最终展示给玩家的自然前情提要：写法应接近小说或电视剧开场前的简短
前情介绍，并能直接衔接第一幕。世界规则、核心悬念和核心矛盾仍可作为大纲推演字段，但只服务
作者侧结构生成，不能带“世界规则：”“核心悬念：”等标签拼入 `intro.background`。

### 3.2 显式支线草稿模型负责生成

作者从故事地图明确点击“生成支线”后，模型可以生成独立的支线语义草稿。它只负责：

- 根据已经确认的终点，反推 1—3 个有因果关系的幕节点；
- 为每个节点提供标题、摘要、可观察的 `must_happen`、`must_not_happen`、猫娘处境和过渡目标；
- 为“来源 → 各幕 → 固定终点”的每次移动提供过渡原因、必须交付、必须保留和语气；
- 作者选择“让生成模型推荐”时，从服务端提供的条件候选中返回一个稳定 `condition_key`；作者已经选定时只解释为何适合该支线；
- 选择较后主线回接点时，逐项说明被绕过关键事实在支线中的承接位置；
- 新结局模式下，先独立生成可编辑的结局语义草稿，再在作者确认后反推过程。

模型不得输出或修改正式 node ID、ending ID、metric ID、数值阈值、比较符、priority、互补路线、
`min_turns`、`recommended_turns`、revision 或 canonical package。`must_happen` 必须是运行时可观察的事件，不得预写玩家
已经说出某句话、做出某项选择或完成关键行动。

回到主线或通往已有结局只执行一次支线草稿模型调用。产生新结局时严格分成两个作者明确触发的
调用：先生成结局草稿；作者确认或修改后，再点击“根据结局生成过程”。两步之间不得自动串联。

### 3.3 程序负责生成或校验

- 确定性生成 schema、meta、intro、catgirl_binding、metric_schema 和 initial_state；
- 根据标题与创作需求生成稳定 story ID；
- 把主线和结局投影为稳定节点 ID；
- 在 N.E.K.O.-DramaticWriting 作者项目中维护不进入 Story Package 的有序 `mainline_node_ids`；
- 不让模型直接决定硬回合门槛；新节点默认使用 `min_turns=3 / recommended_turns=3`，生成 Prompt 以每幕 8 回合为软目标；短篇模型声明的 `expected_turns>8` 会触发当前章节定向续写，要求合并可合并事件，但修订失败仍保留作者可见警告；模型声明的作者侧 `expected_turns` 只保留为作者侧节奏诊断，不会同步到 `recommended_turns`，不产生最短运行门槛，也不触发自动换幕；超过 8 回合、超过 40 回合、无法估算或离幕说明只有观察/等待时，`pacing_diagnostics` 只在作者界面提示，不进入 Story Package 的额外字段，也不参与路线计算；
- 预设和缺省 metric 根据 `relationship_effect` 选择安全限幅：关系型默认每回合增加和减少均为 3，非关系型默认均为 5；作者显式填写的合法限幅保持不变；
- 当亲密关系是主要剧情弧时，主线生成优先使用篇幅范围上半区，并把关系变化拆成由共同经历和已发生事实支撑的阶段；相邻章节只推进一小级，不能把角色表达风格误当成已经建立的亲密关系；
- 主线生成同时产出作者侧 `relationship_arc`：逐幕记录关系表现上限、玩家称呼认知、已经知道的玩家事实、允许与禁止行为，以及本幕提供的关系发展机会；它约束节点生成和支线连续性，但不作为新字段写入 Numeric v2 Story Package；
- 主线生成同时产出作者侧 `character_state_arc`：逐幕分别记录女主、男主和环境的入幕状态、从上一幕延续的事实、状态主体与职责边界，以及猫娘的认知、记忆、自称、人格范围和发声合同。状态线本身不进入 Runtime Session；程序把三方状态、连续事实和边界投影到 `story_beat.character_state`，同时继续把猫娘认知权限写入 `acting_contract`、把边界并入 `must_not_happen`、把连续事实写入目标路线的 `must_preserve`，供当前 N.E.K.O Runtime 消费。由于状态边界会进入负向合同，每项必须以“不得”“禁止”或“不能”开头，正向状态只能写在对应角色状态字段；
- 发热、受伤、昏迷、失声、持有物和地点必须在状态线中明确主体。普通换场不得重新 `fresh_boot`，只有剧情已经明确发生首次启动、真正重启或记忆切断时才可使用受限认知合同；支线和结局必须承接同一状态线，不能交换患者与照护者、转移伤情或重新询问已经确认的身份；
- `relationship_arc.opening_relationship` 必须与开场初始关系一致；未来关系方向只保存在作者项目中，不能再与初始态度拼接进 `catgirl_binding.role_overlay`；正式包中的 `role_overlay` 由首幕结构化阶段确定性生成，只保留关系上限、称呼认知、已知玩家事实和“未来规划不是当前事实”的通用边界；
- 生成器把每幕关系上限、称呼认知、已知事实和至多两项禁止行为压入现有 `story_beat.catgirl_situation` 的末尾，确保 Runtime 按完整句裁剪时优先保留关系合同；隐藏 metric band 继续决定实际亲密度，关系弧只提供剧情上限，不能强制玩家尚未通过行动建立的关系；
- `intro.player_identity` 只投影玩家静态身份，`intro.catgirl_identity` 只投影猫娘静态身份和秘密/困境；进入原因、介入能力、当前动机和长期关系方向留在作者项目中，避免模型把“保护者”“唯一桥梁”等职责描述误当成开场已经建立的关系；
- 失忆、人格重置或意识重置已经在当前幕入场前发生时，关系阶段必须填写 `reset_reason`，关系上限允许向下跨级，但必须回到陌生或戒备，并同步清空或重新介绍称呼和玩家事实；
- 相邻主线幕的关系上限最多变化一级。支线必须承接来源幕的关系与认知边界，回接主线时不得超过回接节点上限或提前获得尚未成立的认知；
- 创建用于地图展示的主线连接草稿，条件保持为空；
- 从现有 metric bands 构造稳定、可读的支线条件候选；
- 根据主线顺序、图可达性、连续性事项和 token 预算构造回接节点候选；
- 把模型返回的 `condition_key` 确定性映射为正式 metric 条件；
- 为原主线出口构造互补条件，并确定性分配 route priority；
- 把语义过渡按固定顺序映射为来源、支线内部和终点 route 的 `transition_contract`；
- 为支线草稿分配稳定 node、ending 和 route ID；
- 在作者应用前完成结构校验、上下文过期检查和预编译；
- 把节点、路线、过渡合同与可选新结局作为一个项目 revision 原子写入；
- 校验节点、路线和结局 ID；
- 校验 metric 引用；
- min、max、initial 和单回合限幅；
- route gate 条件结构；
- priority 唯一性；
- 节点和结局可达性；
- terminal node 与 ending 对应；
- 非结局节点 `min_turns` 必须为 1—20 的整数；
- 可选 `recommended_turns` 必须为 `min_turns`—40 的整数；生成器新节点总是显式写入。旧包不能依靠运行时补字段，必须重新导出声明 `v2.2` 的包；
- canonical JSON 和 package hash；
- 下载文件名；
- N.E.K.O 复验结果。

### 3.4 明确禁止

- 模型直接写入 N.E.K.O 包目录；
- 把多出口且尚未配置数值条件的分支标记为可交付；
- 为编译失败自动增加第二次完整生成；
- 把质量评分或节点修复塞进默认生成链路，或在作者确认前自动改写故事；
- 生成推荐输入并写入 Story Package；
- 生成动态剧情节点交给 N.E.K.O 临时安装；
- 为旧协议添加隐式兼容字段；
- 让支线模型发明 metric、band、阈值、比较符、priority 或路线补集；
- 把完整项目、无关支线、Session、Ledger 或运行时演绎历史发送给支线模型；
- 在作者确认支线草稿前创建空节点、改变 revision 或重接现有路线；
- 在没有合适 metric 时静默新增数值或用无条件多出口绕过编译合同；
- 依赖 node ID 前缀、画布位置或模型推断主线顺序；
- 选择更后回接点后静默丢弃被绕过主线幕的关键事实。

## 4. 用户工作流

### 4.1 新建剧本

基础输入：

- 标题；
- 超过 30 个字的创作想法；
- 题材；
- 基调，可由模型生成后修改；
- 玩家与猫娘的初始关系，由模型生成后修改；
- 内容禁区；
- 篇幅档位。

目标篇幅放在创作想法上方。独立“AI扩写”入口已经删除，顶栏“生成剧情结构”调用主线生成服务。
创作想法必须超过30个非空白字符。初始请求发送当前想法、目标篇幅范围和姓名快照，不发送标题、
题材、已有关系／基调、内容边界或metric。初稿一次调用，失败恢复见4.2，不承诺整个操作只有一次请求。模型返回：

- 世界观、规则、核心悬念与矛盾；
- 剧情主角、玩家角色和双人关系动力；
- 位于目标篇幅范围内的主线章节；
- 一个 Normal 结局；
- 玩家与猫娘的初始关系和整体氛围标签。

第一章发生在玩家首次输入之前。模型可以描写环境、剧情主角的可见行动和两人即将相遇的局势，
但不能替玩家预写对白、选择或关键行动；后续章节同样要给运行时交互留出玩家决定过程的空间。

每章使用1—6项 `ordered_goals`，按现行协议声明主体、来源、交付方式和时点；叙事使用生成姓名快照，协议值仍为 `player / catgirl / shared / environment`。玩家事件须以实际玩家输入为依据，不能预写已完成动作。涉及日期、编号、金额或条款时写清实际值；尚待协商的值保留待定，不能让演绎器凭空补造。事件只作作者素材，不给Runtime增加逐项完成门槛。

服务端确定性检查输出结构、主线数量和 Normal 结局，再把结果投影成主线与结局地图草稿。生成成功后，
保留作者原始创作想法，只回填初始关系和整体基调并进入故事地图；失败时不改动原内容或旧地图。
主线连接线不伪造数值阈值，条件为空；来源节点只有一个出口时表示确定性的顺序推进，可以直接编译。
只有同一来源出现多个出口时，每条路线才必须补齐数值条件。

### 4.2 生成流程

```text
标题 + 创作想法 + 目标篇幅
  -> 固定故事框架，逐幕生成正文与关系／权限规划
  -> 每幕单独摘录开场三方状态与当前处境，最后生成和摘录 Normal 结局
  -> 每阶段保存检查点；失败只续做未完成阶段，保留候选及姓名快照
  -> 服务端确定性投影主线节点、Normal 结局节点和空条件顺序连接
  -> 完整候选先通过当前 N.E.K.O 编译器，再原子替换地图并进入故事地图
  -> 作者配置数值规则
  -> 使用终点先行向导生成支线，或进入高级模式手动编辑
  -> 预览并原子应用支线草稿
  -> 确定性编译
  -> N.E.K.O 当前 v2.2 编译器复验
  -> 下载或本地安装
```

新建生成使用与当前 SDK 一致的 `staged.v1` 协议。框架、每幕写稿、结局和各次状态摘录分别最多三次模型调用；不需修订时 N 幕共 2N+3 次调用，状态摘录最多 600 输出 tokens。失败保留已完成正文与阶段检查点，显式续写不重做已完成阶段；本体编译错误定位后只修对应幕或框架。

旧整稿检查点继续使用 `_MAINLINE_GENERATION_MAX_ATTEMPTS=3` 的原恢复预算：没有可解析候选时重新请求初稿，有候选时只续写校验失败路径。仍失败则显示合同问题、调用记录和可恢复检查点，显式再次生成才接续；重启或读取项目不自动重发。不添加评分驱动的自动全本修订、Planner或客户端叠加重试。

### 4.3 编辑流程

用户应能够编辑：

- 背景和身份；
- 节点 story beat；
- 分支和结局；
- metric 配置；
- route gate 条件；
- route priority；
- transition contract。

### 4.4 支线节点 AI 完善

作者选择手动新增节点时，必须先选择“幕节点”或“结局节点”。作者先填写节点标题和摘要，再显式
点击“AI 完善”。服务端只调用模型一次，输入包含：

- 节点类型；
- 作者填写的标题和摘要；
- 可到达该节点的上游节点；
- 进入该节点的路线条件与过渡合同；
- 本剧数值的名称、含义、范围和增减依据；
- 当前故事背景、猫娘身份覆盖和作者边界。

模型只返回 `must_happen`、`must_not_happen`、`catgirl_situation` 和 `transition_goal`。程序不得让
模型修改节点 ID、节点类型、标题、摘要、ending ID、连接线、阈值或 priority。失败不写项目，也不
自动 Retry、Repair 或 Planner。所有可达路线必须最终到达结局节点；幕节点不能成为支线终点。

“AI 完善”是单节点辅助能力，不承担支线规划，不得在其内部增加节点、连接线或结局。终点先行
向导是独立入口和独立合同，不能通过扩展“AI 完善”接口实现。

### 4.5 终点先行支线向导

首版只允许从“恰好有一个无条件顺序出口”的非结局节点发起，以免自动改写作者已经设计好的
多出口结构。完整流程为：

1. 作者在来源节点点击“生成支线”；
2. 先选择终点：回到主线、通往已有结局或产生新结局；
3. 用自然语言说明想看的偏离、冲突或代价；
4. 从人类可读条件候选中选择触发语义，或允许生成模型在同一候选集合中推荐；
5. 选择短支线 1 幕、标准支线 2 幕或长支线 3 幕；
6. 生成不写项目的语义草稿；
7. 作者检查终点、触发语义、各幕因果链和确定性警告；
8. 点击“应用支线草稿”后，服务端一次性提交完整结构。

首版只有来源节点本身位于作者主线顺序中时，才提供“回到主线”。选择后必须继续询问“回到哪一幕？”。
原顺序出口的下一幕作为推荐默认值，同时按主线顺序列出来源之后的合法节点。候选卡片至少显示目标
标题、简短摘要、将绕过的主线幕和关键事实数量；“通往已有结局”只显示当前结构中合法、可引用的结局。

N.E.K.O.-DramaticWriting 作者项目必须单独保存有序 `mainline_node_ids`，首次主线投影时写入，作者明确调整主线时同步
更新。它只用于作者工具的主线识别、候选排序和连续性分析，不进入 Story Package、canonical bytes
或 N.E.K.O Runtime。不得依赖 `mainline_XX` 前缀、画布坐标或模型判断主线。导入项目没有可靠顺序
时，只能在唯一无歧义的顺序骨架上确定性建立；否则先要求作者在高级地图工具中确认主线顺序，不能
静默猜测。

选择更后节点意味着支线路径会绕过中间主线幕。服务端把每个被绕过幕的 `must_happen` 和通往下一幕
的 `transition_contract.must_deliver` 投影为不透明的连续性事项。首版模型必须逐项返回“在支线中承接”
的位置和原因，不允许 `intentionally_replaced`。服务端除校验完整覆盖外，还把每项原始文本确定性注入
对应新幕的 `must_happen` 或新过渡的 `must_deliver`，不能只相信模型的解释。需要改写既定事实时，
作者退出向导并使用高级手动编辑，同时自行调整依赖该事实的下游合同。

服务端为每个回接候选计算 `minimum_length` 和 `allowed_lengths`。最低长度至少覆盖被绕过幕数，并按
每幕最多保守承接两项连续性事项计算容量；前端只显示允许的 1—3 幕选项。三幕仍不足或上下文超过
16K 硬上限时，候选在模型调用前禁用。

### 4.6 新结局先生成、确认后反推

选择“产生新结局”时，向导不得一次生成并直接落图：

```text
作者描述结局方向
  -> 明确点击“生成结局草稿”
  -> 一次模型调用返回结局标题、摘要、必须发生、不得逆转事实、猫娘处境和收束语气
  -> 作者确认或直接编辑结局草稿
  -> 明确点击“根据结局生成过程”
  -> 第二次模型调用反推 1—3 个幕节点
  -> 统一预览
  -> 原子应用
```

第二次调用必须使用作者确认后的结局，而不是第一次模型原始输出。作者修改结局不触发模型；只有
再次明确点击才生成过程。任一步失败都保留当前向导输入，但不创建正式 node、route 或 ending。

### 4.7 人类可读条件与确定性映射

默认界面不要求作者编辑原始数值和阈值，但不能把触发逻辑完全隐藏。服务端根据现有 metric 的
含义、增减依据和合法 bands 构造候选，例如：

```json
{
  "key": "condition_02",
  "label": "当信任达到愿意托付秘密的程度",
  "metric_name": "信任度",
  "band_label": "愿意托付秘密"
}
```

发送给模型的候选只包含本次草稿上下文内稳定的不透明 key 和叙事语义，不需要包含 metric ID、
比较符、阈值或 priority。key 只能在同一 `base_revision` 和上下文指纹下使用，不能跨项目复用。
服务端私有映射负责把 key 还原为正式条件。首版一个候选只对应一个 metric band：

- 目标区间高于初始值时映射为单侧下界，达到目标状态后继续增长仍满足支线；
- 目标区间低于初始值时映射为单侧上界，降到目标状态后继续下降仍满足支线；
- 初始值已经处于目标区间时才使用该区间的完整上下界；
- 原顺序出口始终映射为正式支线条件在整数取值域内的严格补集。

两个出口必须覆盖原 metric 的整个合法整数范围，不能重叠、断档或依赖同 priority 猜测胜负。高级
路线编辑器可以展示和修改正式表达式；一旦作者修改，后续按普通手动路线合同校验。

下列情况不提供候选，也不调用模型：

- 项目没有 metric；
- bands 重叠、断档或越界；
- 只有一个覆盖全范围的 band；
- band 仍是“低位/中位/高位”“当前状态”等无法表达剧情含义的占位文案；
- 来源节点已经有多个出口或唯一出口不是无条件顺序推进。

界面应引导作者完善数值规则，或明确确认添加一个可编辑的预设 metric。服务端不得静默创建数值，
也不得让模型依据自然语言直接发明阈值。

### 4.8 草稿生命周期与原子应用

支线草稿不是 Story Package 的一部分。创建草稿时记录：

- `project_id` 与 `base_revision`；
- 来源节点、原目标和已选终点；
- 相关上游节点与 metric 规则的上下文指纹；
- 作者方向、长度和候选条件版本；
- 模型结果与确定性预览结果。

应用前重新检查 project revision 和上下文指纹。任一来源节点、原出口、目标、相关 metric 或上游
事实已经变化时，返回稳定的“草稿已过期”，不得套用到新结构。通过后先在内存副本中完成 ID 分配、
互补路线构造、结构检查和编译，再以一个新 revision 原子替换项目；任何失败都保持原项目字节不变。

草稿生成失败、作者取消或草稿过期，不得留下空节点、孤立结局、半条路线或 revision 变化。

用户不需要直接编辑：

- JSON；
- schema；
- package hash；
- Session 或 Ledger 字段；
- 运行时推荐输入。

## 5. 高级数值选项

### 5.1 预设数值

第一版建议提供以下预设：

- 好感度；
- 信任度；
- 厌恶度；
- 戒备度；
- 亲密度；
- 压力值；
- 恐惧度；
- 勇气值；
- 怀疑度；
- 线索进度；
- 自定义数值。

预设只是填写模板，不代表所有剧本必须使用，也不把恋爱题材写成默认方向。

### 5.2 每项数值的表单字段

| 字段 | 说明 | 要求 |
| --- | --- | --- |
| 数值名称 | 玩家和作者理解的名称 | 必填 |
| 数值含义 | 该数值在本剧中代表什么 | 必填 |
| 关系演绎作用 | `positive / negative / none`，表示越高越亲近、越高越疏远或不影响关系距离 | 预设确定默认值，自定义默认 `none`，作者可改 |
| 初始值 | Session 开始时的值 | 必填 |
| 最小值 | 状态下界 | 默认值可调整 |
| 最大值 | 状态上界 | 默认值可调整 |
| 单回合最大增加 | 防止一次对话跳满 | 必填或安全默认 |
| 单回合最大减少 | 防止一次对话清空 | 必填或安全默认 |
| 增加依据 | 哪些玩家行为应增加 | 必填 |
| 减少依据 | 哪些玩家行为应减少 | 必填 |
| 玩家可见性 | 固定写入 `hidden`，不提供表单选项 | 程序投影 |
| 区间表现 | 不同数值区间的关系状态 | 可由模型建议、作者确认 |

安全默认由程序按 `relationship_effect` 确定：`positive / negative` 的关系型数值增减上限均为 3，`none` 的非关系型数值增减上限均为 5。该规则只填补作者未显式设置的字段，不覆盖作者已经确认的合法值。

### 5.3 预设数值的默认文案

预设必须提供可编辑的初始含义和示例，不把模板锁死。

关系演绎作用由预设显式声明：好感度、信任度、亲密度为 `positive`；厌恶度、戒备度、怀疑度为 `negative`；压力值、恐惧度、勇气值、线索进度为 `none`。程序不能根据名称或题材推断自定义数值的作用。

例如“信任度”：

```text
含义：猫娘愿意相信玩家承诺并交付真实信息的程度。

增加依据示例：
- 玩家坦诚说明目的；
- 玩家兑现承诺；
- 玩家尊重猫娘表达的边界；
- 玩家在不索取回报的情况下承担风险。

减少依据示例：
- 玩家说谎或故意隐瞒关键目的；
- 玩家违背承诺；
- 玩家强迫猫娘交付不愿公开的信息；
- 玩家利用已经获得的秘密伤害猫娘。
```

用户可以修改这些依据，使同一个“信任度”适配悬疑、恋爱、冒险或日常题材。

### 5.4 自定义数值

新增自定义数值时，以下三项缺一不可：

1. 这个数值代表什么；
2. 什么玩家行为会增加；
3. 什么玩家行为会减少。

自定义数值还必须满足：

- 名称不能和已经选择的数值重复；
- 规范化 ID 不能与已有 metric ID 冲突；
- 增加和减少依据不能完全相同；
- 不能只写“根据剧情判断”“由 AI 决定”等无可执行依据；
- 至少各提供一条明确依据；
- 数值范围和初始值合法。
- 关系演绎作用只能从 `positive / negative / none` 中选择；未确认时保持 `none`，不能按名称猜测。

### 5.5 语义重叠提示

同时选择语义高度接近的数值时只产生软提示，例如：

- 好感度与亲密度；
- 信任度与自定义“信赖值”；
- 厌恶度与反向好感度；
- 戒备度与怀疑度。

提示作者说明差异，但不自动删除或合并，避免程序替作者改变设计。

### 5.6 bands 的双重用途

bands 不只是作者预览文案，也是引导式支线创作的语义条件来源。可交付编译只要求区间结构合法；
要进入支线向导，还必须至少有两个能区分剧情状态的有效标签。默认模板应使用“仍保持距离”
“愿意说明真实顾虑”“愿意托付重要秘密”一类题材可理解文案，而不是仅写“低位”“中位”“高位”。

编译合法但语义过弱时，普通手动编辑仍可使用，支线向导单独显示阻断说明。这不会改变 Story Package
合同，也不会把文案质量警告升级成整个项目的编译硬错误。

## 7. DTO 与支线草稿合同

### 7.1 Numeric v2 项目作者数据

当前项目作者数据示例：

```json
{
  "title": "清河晚风",
  "brief": "多年未见的两人在小镇重逢，决定留下还是分别。",
  "genre": "小镇爱情",
  "tone": ["克制", "温柔"],
  "relationship": "少年时代熟悉但多年没有联系的邻居",
  "content_boundaries": [
    "不使用突然失忆",
    "不通过重病强迫和解"
  ],
  "length_preset": "short",
  "metrics": [
    {
      "preset": "trust",
      "name": "信任度",
      "description": "她愿意相信玩家会认真留下的程度。",
      "relationship_effect": "positive",
      "min": 0,
      "max": 100,
      "initial": 20,
      "increase_limit": 6,
      "decrease_limit": 8,
      "increase_criteria": [
        "兑现承诺",
        "尊重她是否愿意谈过去"
      ],
      "decrease_criteria": [
        "敷衍她的担忧",
        "利用她尚未公开的秘密"
      ],
      "visibility": "hidden"
    }
  ]
}
```

作者项目外壳另存以下结构元数据：

```json
{
  "authoring": {
    "mainline_node_ids": [
      "mainline_01",
      "mainline_02",
      "mainline_03",
      "mainline_04"
    ]
  }
}
```

`mainline_node_ids` 引用稳定 node ID，但顺序本身不投影到 Story Package。删除、替换或明确调整主线
后必须在同一项目 revision 内更新；不能存在未知、重复或 ending ID。相邻两个主线节点之间必须存在
且只存在一条直接指向下一主线节点的 route，否则对应区段标记为主线顺序失效。仅拖动画布不会改变
主线顺序。

所有 metric 固定对玩家隐藏。高级选项不提供可见性配置；服务端归一化和最终编译都必须将
`visibility` 确定性写为 `hidden`。

服务端必须先校验和规范化 DTO，再调用模型。用户自定义文本全部作为数据区进入 Prompt，不能覆盖
系统合同。

### 7.2 支线意图 DTO

作者发起向导时提交意图，不提交正式 route gate：

```json
{
  "base_revision": 12,
  "source_node_id": "node_station",
  "endpoint_mode": "mainline",
  "endpoint_node_id": "node_old_house",
  "direction": "她误以为玩家又要不告而别，两人先分开调查车票的来源。",
  "length": 2,
  "condition_selection": {"mode": "recommend"}
}
```

`endpoint_mode` 只允许：

- `mainline`：`endpoint_node_id` 必须来自本次 `branch-options` 返回的可用回接候选；
- `existing_ending`：`endpoint_node_id` 指向已有结局节点；
- `new_ending`：第一次使用独立的结局草稿请求；作者确认后，过程请求携带 `ending_draft_id` 和当前编辑后的结局合同。

当前 API 使用 `length: 1 | 2 | 3`。回接主线时该值还必须属于候选返回的 `allowed_lengths`。
`condition_selection` 为 `{ "mode": "recommend" }` 时允许模型从服务端候选中推荐；为
`{ "mode": "fixed", "key": "..." }` 时使用作者已经选择的 key，模型不得改选。

`branch-options` 的每个回接候选至少返回：

```json
{
  "target_node_id": "mainline_04",
  "title": "山顶星空下的告白",
  "summary": "两人在山顶面对彼此真正担心的未来。",
  "recommended": false,
  "skipped_nodes": [
    {"id": "mainline_03", "title": "夏日市集里的默契"}
  ],
  "continuity_items": [
    {"key": "continuity_01", "text": "两人已经在共同完成工作时建立基本默契"}
  ],
  "minimum_length": 2,
  "allowed_lengths": [2, 3],
  "estimated_input_tokens": 9300,
  "available": true,
  "unavailable_reason": null
}
```

原顺序出口目标固定为第一项并标记 `recommended: true`。后续项按 `authoring.mainline_node_ids` 排序。
目标会形成环、已经失效、主线顺序不可靠，或预计必要输入超过 16K tokens 时返回不可用原因，前端
可以解释但不能提交该目标。

### 7.3 支线过程模型输出

模型返回语义草稿，不返回正式 Story Package：

```json
{
  "condition_key": "condition_02",
  "condition_reason": "只有她已经愿意相信玩家会留下，这次误会才适合转化为共同调查。",
  "scenes": [
    {
      "title": "被撕下的车票",
      "summary": "两人在站台分别追查同一张旧车票的来源，误会逐步显出人为痕迹。",
      "must_happen": [

      ],
      "catgirl_situation": "她仍在生气，但开始怀疑自己看到的并不是全部事实。",
      "transition_goal": "让两人因同一条线索重新汇合，并自然进入旧屋节点。"
    }
  ],
  "transitions": [
    {
      "from": "source",
      "to": "scene:0",

      "must_deliver": ["猫娘拿出被撕下的旧车票"],
      "must_preserve": ["两人尚未确认车票是谁留下的"],

      "must_preserve": ["幕后人的身份仍未揭晓"],

```

服务端必须拒绝未知 `condition_key`、幕数不符、空的可观察事件、预写玩家决定、引用未知角色或
改变已确认终点的候选。`transitions` 必须严格为幕数加一条，并按 `source -> scene:0 -> ... ->
endpoint` 连续排列；引用、数量或必要字段不合法时直接返回稳定问题，不自动请求模型修正。

`continuity_handling` 必须把本次提供的每个 continuity key 恰好处理一次。首版 `mode` 只允许
`carried`，并必须指向有效 `scene:n` 或 `transition:n`。模型不能新增、遗漏、改写 key，也不能用

程序只在来源分叉的第一条支线路线应用选中的 metric 条件。支线内部以及最后进入回接节点或结局的
路线使用无条件顺序推进；原主线路线保留原有 `transition_contract`，只把空条件替换为支线条件的
确定性补集。

### 7.4 新结局模型输出

新结局的第一次模型调用只返回：

```json
{
  "title": "没有寄出的远行信",
  "summary": "两人接受彼此仍会害怕失去，但决定共同面对下一次离开。",
  "must_happen": [
    "猫娘亲手交出一直没有寄出的信"
  ],
  "irreversible_facts": [
    "两人已经坦白当年分别的真实原因"
  ],
  "catgirl_situation": "她不再用沉默测试玩家是否会留下。",
  "tone": "克制、释然、保留未来感"
}
```

该对象先进入 `ending_review`，作者可直接编辑。只有作者明确确认后，它才作为第二次支线过程模型
调用的固定终点。服务端生成正式 terminal node 和 ending ID，不采用模型文本作为 ID。

### 7.5 服务端支线草稿

服务端响应还必须附带 `draft_id`、`base_revision`、`context_fingerprint`、草稿状态、终点摘要、
人类可读触发条件、确定性问题和高级条件预览。草稿状态至少包括：

```text
新结局：generating_ending -> ending_review -> generating_path -> preview -> applying -> applied
已有终点：generating_path -> preview -> applying -> applied
生成失败：generating_ending | generating_path -> failed
上下文过期：ending_review | preview -> stale
应用失败：applying -> preview，并附带确定性错误
```

回到主线和已有结局模式可从创建直接进入 `preview`。`applied` 后同一 `draft_id` 重复提交必须返回
同一结果或稳定幂等响应，不能重复创建节点。

## 8. 生成 Prompt 边界

### 共享写作与评改原则

以下规则已在两端 `generation/numeric_v2.py` 与 `generation/runtime_rules.py` 的实际链路同步，覆盖主线、续写、完善、支线、事实检查、证据、文学、方案复核和限定修订；不是新增协议或模型保证：

- 关键演绎优先由男女主推进，配角仅作必要背景、简短线索与直接回应，不靠增加配角任务或反复交接凑篇幅；保留已有必要职责及玩家选择权。
- 用具体主体、前提、行为和可见结果替代抽象“体现难度”；条件具备后交付结果，不追加无关难题。
- 区分开场演完后的状态、幕内变化和未来计划；道具用途／预计取得不等于实际持有，作者来源ID不等于玩家已执行。
- 来源邀请、过渡桥段和目标开场应兑现同一去向、时段及开始的活动；幕内移动、休息和等到天亮不自动授权另一个地点或次日新安排，不靠虚构捷径、停业或改主意圆场。
- 玩家可以主动发起已公开下一步；普通换幕接受／主动请求与自然结束分开。最终互动及必要回应完成后允许自然结束，不追加确认或在关闭输入后发问。
- 每轮 `[-5,5]` 为硬范围，推荐回合和阈值按有效行为约±2估算；重复同一事件不刷分，新的有效行为可连续计分。静态可达性不等于真实体验可达。

共享规则对应问题2.80、2.92、2.103、2.110；本体复核、额外状态和提速实验未采用时，不向工坊增加对应字段或调用。

### 8.1 初次主线 Prompt

主线系统 Prompt 只要求模型产出主线大纲和一个 Normal 结局，并明确：

- 剧情主角固定为女性，由当前猫娘演绎；玩家角色固定为男性；
- 新建生成任务由本体提供 `cast_names`：当前猫娘名和用户昵称，角色归属固定；姓名成对保存到 `intro.player_name/catgirl_name`。N.E.K.O 开演时仍按当时姓名适配，未披露时称“你”；
- 不生成 metric 或阈值；
- 不生成支线；
- 不生成 interaction rule；
- 不生成 available interaction IDs；
- 不生成 Choice；
- 不生成推荐输入；
- 不生成 Session 状态；
- 只写剧情边界，不写完整逐回合对话；
- `world.background` 只写自然前情提要，不列出世界规则、悬念或矛盾标签，并能自然衔接第一幕；
- 第一章不得假定玩家已经说话、选择或完成关键行动。
- 每章使用现行 `ordered_goals` 输出 1—6 项原子目标，明确 owner、delivery_type、evidence_mode、anchors、sources、timing、dialogue_policy_after；职责及引用保持协议值，正文使用对应角色姓名；
- 不把多个条件、数量、期限或范围合并成一个复合事件，具体日期、编号、金额和条款必须直接写入对应事件；

新生成用户消息包含 `core_idea`、`length` 和 `cast_names`。`length` 明确提供 preset、主线章节最小值和最大值；仅旧无姓名调用继续使用“女主／男主”槽位。
模型输出 world、双主角、relationship、tone、关系/状态规划、关键道具、mainline_chapters 和 ending
的结构化 JSON。服务端强制检查输入超过 30 个非空白
字符、必需字段形状、主线章节数量和 `ending.type == normal`；每章 400 字与总计 2000 字属于 Prompt 内容要求，
不作为失败即丢弃的语言硬规则。通过结构检查后，服务端确定性格式化创作需求并投影地图草稿。
投影时 `intro.background` 只取 `world.background`；`world.rules`、`core_mystery` 和
`core_conflict` 不进入玩家可见前情提要。

服务端把现行 `ordered_goals` 投影为带稳定ID的 `story_beat.goals` 作者元数据，分别保存主体、来源、交付方式和时点。`catgirl_progress_events / catgirl_progress_event` 是历史模型输出形状，不作为新生成协议；运行时不逐项追踪这些目标，不以其证据或全部完成作为换幕门槛。旧作者字段是否可编辑／编译由实际合同决定，不能据此放宽玩家归属或补造已发生事实。

### 8.2 支线过程 Prompt

支线系统 Prompt 要求模型从固定终点反推因果，但按玩家实际经历的正向顺序输出，并明确：

- 来源、原出口、终点和目标幕数不可修改；
- 只能返回提供过的 `condition_key`；
- 不得返回 metric ID、数值、阈值、比较符、priority、route 或正式 ID；
- 每幕安排至少一个可见的完整互动与结果，作为作者素材；Runtime不按目标清单逐项判定或锁存完成；
- 不得把玩家尚未发生的对白、选择、承诺或行动写成既成事实；
- 每幕必须推动下一幕或已确认终点，不能用无关插曲填充数量；
- `transitions` 必须从 `source` 连续经过每个 `scene:n` 到 `endpoint`，每条都包含可执行的
  `reason`、`must_deliver`、`must_preserve` 和 `tone`；
- 选择较后主线节点时，必须逐项处理提供的 continuity key，不能假装被绕过剧情已经发生；
- 不得提前兑现终点事件，也不得推翻上游既定事实和内容禁区；
- 只返回结构化语义草稿，不写完整对话、推荐输入、Session 或 Ledger。

如果作者已经选择条件，模型只能解释它与支线的因果关系；如果作者选择“由生成模型推荐”，模型也
只能从同一候选集合中选择。未知 key 或自行改写 key 均视为候选失败，不做模糊匹配。

### 8.3 新结局 Prompt

新结局 Prompt 只接收作者的结局方向和必要故事上下文，输出第 7.4 节的结局语义字段。它不得生成
通往结局的过程、路线条件、正式 ending ID 或玩家已做出的决定。作者确认后的结局对象在第二次调用
中作为不可改写目标；第二次模型不得“优化”或替换已经确认的结局。

### 8.4 支线上下文投影

支线生成不发送完整项目。服务端按固定结构投影：

| 上下文 | 内容 | 范围 |
| --- | --- | --- |
| 全局设定 | 背景、双角色身份、关系、基调、内容禁区 | 各字段经过项目级长度校验 |
| 来源节点 | 标题、摘要、全部演绎约束和过渡目标 | 完整包含 |
| 近期上游 | 当前主线路径上最近 1—2 个上游节点及必须发生事实 | 完整包含 |
| 更早事实 | 当前主线路径中更早的 `must_happen` | 按距离由近到远、原文去重后在预算内收纳；超出即省略 |
| 原出口 | 原路线和原目标的叙事摘要 | 完整包含 |
| 固定终点 | 回接节点或结局的完整作者合同 | 完整包含 |
| 被绕过主线 | 来源下一幕到回接目标前的标题、摘要、`must_happen` 与路线 `must_deliver` | 只在较后回接时完整包含 |
| 连续性事项 | 从被绕过主线确定性提取的不透明 key 和原文 | 全部包含 |
| 数值语义 | 相关 metric 名称、含义、增减依据和 band 标签 | 不发送正式阈值映射 |
| 条件候选 | `condition_key` 与人类可读语义 | 只发送本次合法候选 |
| 作者意图 | 支线方向、长度和已确认结局草稿 | 完整包含 |

未被选为回接目标的后续主线、无关支线、无关结局、图坐标、编译缓存、canonical bytes、revision
历史、Session、Ledger、Actor
记录和 Evaluator 记录一律不进入 Prompt。服务端不得再调用模型总结上下文；所有取舍都由固定投影
规则完成，并在测试中可复现。

### 8.5 模型能力与 token 预算

模型配置必须支持可靠的结构化 JSON，并满足本次“系统 Prompt + 输入上下文 + 最大输出”的总上下文
要求。连接测试通过不等于支线能力通过，发布前必须使用实际生产模型完成短、中、长支线压力测试。

首版预算：

- 支线模型输入目标为 8K—12K tokens；
- 输入硬上限为 16K tokens；
- 支线过程最多 3 幕，输出上限为 6K tokens；
- 新结局草稿输出上限为 2K tokens；
- 调用前必须使用供应商 tokenizer，或采用偏保守且有回归样本的估算器，预检总预算。

超过目标预算时，只能按固定规则移除重复描述和非必要更早事实，不能截断来源节点、固定终点、角色
身份、内容禁区、被绕过主线、连续性事项或条件候选。服务端应在 `branch-options` 阶段估算每个回接
候选；仍超过 16K 的候选直接标记不可用。提交时再次预检，或当前模型无法预留所需输出空间时，返回稳定错误
`branch_context_too_large` 或 `model_context_insufficient`，引导作者缩短相关字段；不得带着截断上下文
继续生成。

每次调用记录输入预算分项、估算 tokens、实际输入/输出 tokens、模型标识和草稿 ID，用于质量压测，
但不得记录 API Key 或把模型内部推理写入项目。

### 8.6 调用与失败原则

当前调用边界：

- 首次主线先生成完整候选；确定性结构校验失败时只续写失败路径，不按文学评分自动改写；
- 回到主线或已有结局的每次显式支线生成只有一次候选；
- 新结局严格使用“结局草稿一次 + 作者确认 + 过程草稿一次”；
- 作者完成地图后执行一次确定性编译；
- 当前操作的生成恢复预算耗尽或模型调用失败时，返回稳定错误；有可恢复候选时保存检查点供作者显式继续；
- 编译失败一次返回全部硬错误；
- 主线只使用第 4.2 节所述的现有恢复流程，不因文学评分另加全本重写、Planner 或客户端叠加重试；支线与节点操作不继承主线恢复预算。

### 8.7 显式质量评分与节点修复

- 默认生成、支线生成、节点完善、编译和发布均不自动触发评分；
- 作者在剧情概览点击评分，或调用方显式调用 SDK 的 `assess_quality` 后，依次执行事实检查、发现事实问题时的一次证据复核、六维文学评分，以及存在可执行修订建议时的一次方案复核。完整流程为 2—4 次模型请求，每阶段一次；任一阶段失败均不保存半份报告或覆盖旧完整报告，并返回具体失败阶段；
- 六维文学评分覆盖人物塑造、情节构思、主题思想、文笔风格、叙事节奏、情感共鸣，各按 0—100 分评价，单项低于 75 分视为不合格。所有原问题、证据复核结论和修改建议仍展示，包括高分维度的轻微问题。低分维度须有问题依据；被证据复核支持的事实 major/blocking，以及文学 major/blocking，使报告不通过；被否定的事实指控不能继续作为扣分依据；
- 评分模型接收一个精简 JSON：`author_intent`、`characters`、`metrics`、`key_props`、`mainline`、`branches`、`endings`。保留作者原始创作要求及实际入幕状态、边界、目标交付时点和演绎合同；结局正文摘要与结局记录摘要分别保留，不能在投影时掩盖冲突。其中支线包含来源节点、可读入口条件、必要数值比较、支线节点和终点；不发送回合预算、priority、编辑器状态、草稿或编译结果；
- 评分报告包含六维雷达图、数值指标数量建议和人物关系优化建议。数值建议只讨论新增、删除或合并指标，不直接修改具体阈值；
- 评分只保存作者侧报告，不进入 Story Package，也不改变内容 revision；每项问题必须包含稳定 `issue_id`、维度、严重度、目标节点、问题说明、修改方案、预期结果和必须保留内容；
- 问题指向已有路线 ID 时，仅按当前图的唯一归属转为来源节点 ID；未知或存在多个来源的 ID 仍拒绝，不从自然语言猜测归属，不将桥段问题改派给目标幕。最终报告和地图高亮仍只使用节点 ID；
- 最终对白和真实玩家体验尚未发生，文笔、节奏和共鸣只能评价当前设计潜力，报告不得声称已经观察运行时结果；
- 查看报告不会修改任何节点。评分完成后，故事地图只高亮可通过修改既有节点文本执行的建议节点；人物关系建议若同样不涉及结构调整，也进入高亮范围；
- 作者点击高亮节点后选择是否优化。选择“是”或“否”都会清除本轮全部高亮；只有选择“是”才把该节点关联的六维问题和人物关系建议合并为一次模型调用，并且只允许修改被点击的一个节点；
- 服务端确定性判断方案是否只需改既有节点文本；涉及新增、删除、拆分、重连节点、路线、条件或回合预算的结构方案继续展示，但标记为需要作者在故事地图手动处理，不提供自动修复入口；
- 定向修复要求当前 revision 下未过期且 `repair_plan_version=3` 的完整报告；旧报告仍可查看，但须重新评分后才能优化。执行前重新核验节点、逐字段授权、保护范围及方案复核肯定结果，不能凭旧高亮或模型的 `ready` 放宽权限；
- 节点标题、`story_beat` 的现有演绎字段，以及结局节点对应标题和摘要，仅能在该方案实际授权的范围内修改；不得修改 ID、类型、路线、metric、阈值、priority、`min_turns` 或 `recommended_turns`；
- 定向修复原子写入后，旧评分标记为 `stale`。系统不自动重评、不自动继续其他方案；作者检查节点后自行决定是否再次评分。

## 10. 编译器硬校验

必须阻止：

- schema 不是 `neko.story.numeric.v2`；
- 顶层必需字段缺失；
- metric 名称、含义或增减依据为空；
- 自定义 metric 缺少增减依据；
- metric ID 重复；
- min >= max；
- initial 越界；
- 单回合限幅不是正整数；
- bands 重叠、断档或越界；
- route gate 引用未知 metric；
- route gate 阈值超出 metric 范围；
- route gate 引用未知目标节点；
- 不支持的条件类型；
- priority 不是整数；
- 同一源节点存在无法解决的同优先级冲突；
- start node 不存在；
- 非终局节点没有任何可达后续剧情；
- 节点不可达；
- 结局不可达；
- terminal node 没有 ending；
- transition contract 缺少 must_deliver；
- `recommended_turns` 不是整数、小于 `min_turns` 或大于 40；
- Story Package 包含 v1 interaction rule、available interaction 或 choices；
- 模型输出 Session、Ledger、revision 或当前数值字段。

应用支线草稿前还必须阻止：

- 来源不是非结局节点，或不再只有一个无条件顺序出口；
- 回接目标不在当前主线候选中、会形成环、顺序已变化，或结局引用已经失效；
- 草稿 `base_revision` 或上下文指纹过期；
- `condition_key` 不属于该草稿保存的候选集合；
- 模型输出幕数与作者选择不一致；
- continuity key 缺失、重复、未知、placement 无效，或待作者确认的改写尚未确认；
- 新节点缺少可观察的 `must_happen` 或必要过渡字段；
- 正式条件与原出口补集存在重叠或断档；
- 内存副本无法通过完整 Numeric v2 编译。

## 11. 软质量警告

以下问题只警告，不触发第二次模型生成：

- metric 数量过多；
- metric 语义高度重叠；
- 某个 metric 没有被任何 route gate 使用；
- 某条路线条件很难从初始值和单回合限幅达到；
- 多个结局条件差异过小；
- story beat 重复；
- transition contract 太抽象；
- 篇幅明显偏离用户选择，但结构仍然闭合；
- metric bands 文案过于机械或题材无关。

软警告必须显示给作者，但不阻断下载和安装，除非 N.E.K.O 当前编译器把对应问题定义为硬错误。

## 12. 可达性分析

编译器应在不调用模型的情况下执行静态可达性分析：

1. 从 initial metric state 开始；
2. 使用每项 metric 的单回合最大正负变化计算理论可达范围；
3. 检查 route gate 阈值是否可能达到；
4. 从 start node 遍历所有理论可达目标；
5. 确认至少一个 ending 可达；
6. 标记理论不可达节点和结局；
7. 检查两个永远同时满足且同 priority 的路线冲突。

复杂叙事是否自然不作为硬数学证明；编译器只保证结构上存在可达空间。

## 13. 预览

N.E.K.O.-DramaticWriting 预览不运行完整猫娘 Actor，只展示作者数据：

- 背景和身份；
- metric 初始值和 bands；
- 剧情图；
- 每条 route gate 条件；
- transition contract；
- ending；
- 静态可达性报告；
- N.E.K.O 编译结果。

支线草稿预览额外显示：

- 来源节点、原顺序路径和固定终点；
- 按正向顺序排列的 1—3 个新幕节点；
- 人类可读触发语义和模型给出的选择原因；
- 原主线路径的人类可读互补语义；
- 确定性可达性、结构问题和上下文是否仍有效；
- 折叠在“高级条件”中的正式 metric 表达式与 priority。

首版不提供数值路径模拟器，也不要求作者手工调整隐藏值来证明路线。路径覆盖、互斥和理论可达性
由确定性分析直接报告。支线向导还要按每条可达入口情景做轻量节奏估算：按每轮正常变化约 2 点、
最多额外 8 轮计算达到阈值所需回合；某方向限幅低于 2 时使用实际限幅。候选分为正常节奏可达、
仅理论可达和不可达三级；自动推荐只能看到正常节奏可达候选，不可达候选禁止应用。该估算不展示
隐藏值，也不是逐回合路径模拟器；需要精细控制的作者进入高级路线编辑器。


作者工作台编辑持久化项目；所有写请求携带 base revision。生成、编译和复验结果必须绑定项目
revision 或 package hash。`export` 返回已经复验的 canonical bytes，浏览器不重新序列化。

`GET branch-options` 不调用模型，返回来源资格、人类可读条件候选、已有结局，以及按作者主线顺序
排列的回接候选。每个回接候选附带被绕过幕、连续性事项、预计输入 tokens 和阻断原因。

只执行新结局生成并返回 `ending_review`；作者编辑后的结局随第二次 `POST branch-drafts` 一并提交，
编辑动作本身不调用模型。回接主线或已有结局时，`POST branch-drafts` 只执行一次过程生成并返回
`preview`。`apply` 携带草稿 ID 和 base revision，并按第 4.8 节完成过期检查、内存编译、幂等保护
和项目原子提交。草稿 API 不得写入 N.E.K.O 包目录或 Runtime 数据。

安装必须：

- 使用 N.E.K.O 当前配置解析出的数据根目录；
- 只写入 `theater/numeric_v2/packages`；
- 不静默覆盖相同 story ID；
- 不写入 Session 目录；
- 不删除任何现有 Story Package；
- 写入前再次运行 N.E.K.O v2.2 编译器。

- all/any；

## 19. 验收标准

产品验收：

- 作者能在高级选项中选择预设 metric；
- 作者能添加自定义 metric；
- 所有 metric 都有清楚的含义、增加依据和减少依据；
- 首次生成结果只包含主线、一个 Normal 结局和无条件顺序连接；
- 生成器不再要求作者预写玩家每轮可能说的话；
- 新作者能先选择终点，再生成 1—3 幕支线，不需要创建空节点或手填阈值；
- 选择回到主线后，新作者能看见并选择具体主线幕，且明确知道会绕过什么；
- 较后回接不会把被绕过主线事实静默当作已经发生；
- 新结局必须先可见、可编辑地确认，再反推通往它的过程；
- 默认界面能说明“什么剧情状态会进入支线”，而不是完全隐藏触发逻辑；
- 没有合适 metric 时明确引导完善规则，不静默发明数值；
- 每个多出口分支都能看见明确数值条件；单出口主线明确显示为顺序推进；
- 每条正式路线都有供 N.E.K.O 平滑过渡的合同；
- 下载包能被 N.E.K.O v2.2 直接导入。

架构验收：

- 首次生成只有一次主线候选；已有终点支线一次；新结局按作者确认边界分成两次；
- 不新增自动 Planner、Repair、Retry 或默认评分；显式评分和逐项确认修复必须遵守 8.7 的节点范围；
- 支线模型不生成正式 metric、阈值、路线、ID、priority 或 `min_turns`；
- 上下文投影和 token 预算可测试、可观测，且不发送完整项目和 Runtime 状态；
- 支线应用通过 revision、指纹、幂等和内存编译后原子提交；
- 主线顺序仅存于 N.E.K.O.-DramaticWriting 作者项目，不污染 Story Package 和 Runtime；
- Numeric v2 只使用自己的 canonical 编译产物；
- 应用支线不改变 N.E.K.O Runtime 或 Story Package 合同；
- Numeric v2 不隐式兼容旧协议；
- 推荐输入不进入 Story Package；
- Session 和运行时数值不进入 N.E.K.O.-DramaticWriting；
- 跨仓库 fixtures 和编译结果一致。
- 主线与支线生成都要求提供非任务化 `narrative_focus`；每幕可选声明 `expected_turns`，程序据此生成作者侧节奏诊断并在支线预览中显示自然离幕动作缺失、非行动式出口或预计过长。

## 20. 当前默认值

以下为当前实现与测试锁定的默认值：

1. 每个剧本最多启用 4 个 metric。
2. 预设 metric 使用 0..50、初始值 20；`relationship_effect` 为 `positive / negative` 时默认单回合增加和减少限幅均为 3，为 `none` 时均为 5。作者显式填写的合法限幅不被默认值覆盖。
3. 所有 metric 固定对玩家隐藏，不提供可见性选项。
4. 新非结局节点默认使用 `min_turns=3`、`recommended_turns=3`；生成 Prompt 以每幕 8 回合为软目标，若生成结果声明 `expected_turns`，只在作者侧保留 8/40 回合及非行动式出口诊断，不写入 Runtime 的 `recommended_turns`。作者仍可在合法范围内编辑；两者都不限制玩家输入次数、不触发节点推进。
5. 支线向导首版只支持一个无条件顺序出口的来源节点。
6. 回接主线先询问具体节点；原出口目标默认推荐，并可选择后续合法主线幕。
7. 默认显示人类可读触发语义，原始 metric 条件只在高级区域展示。
8. 首版不提供数值路径模拟器。
9. 内置 preset 已提供可读语义 bands；自定义数值必须由作者补全可读且连续覆盖范围的 bands，
   仍是“当前状态”等占位文案时不能调用支线模型，只能先完善数值或使用高级手动编辑。
